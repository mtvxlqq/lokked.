# Lokked — план реализации v2 (Linux + Windows + мобилка)

Приложение для учёбы: таймеры по предметам (Pomodoro, свободный отсчёт, «чёрный экран»),
учебные карточки с самопроверкой, статистика.

**Целевые платформы:** Fedora 43 / GNOME 49 / Wayland (основная, v1) → Windows 10/11 →
Android → iOS (последним, см. 0.4).

---

## 0. Стек и почему именно он

### 0.1 Выбор: Tauri 2

**Rust (ядро + доступ к системе) + TypeScript/React (интерфейс) + SQLite (данные).**

Tauri 2 собирает **один** проект под Linux, Windows, macOS, Android и iOS. Это не
«ядро общее, UI переписываем» — это буквально один и тот же код везде.

Почему не GTK4 (вариант из v1): мобилки нет и не будет.
Почему не Flutter: он лучше на мобилках, но Linux-десктоп у него — самый заброшенный
таргет, а Linux у тебя основная система, в которой ты будешь жить каждый день.
Почему не Electron: не умеет мобилки вообще, и 300 МБ RAM за список карточек — перебор.

Что конкретно выигрываем на этом стеке:

- **Формулы решаются нормально.** В GTK-плане был костыль с рендером LaTeX через
  matplotlib в PNG. Здесь — KaTeX, три строки, полноценный LaTeX, мгновенный рендер.
- **«Чёрный экран» — это `background: #000` и `position: fixed`.** Всё.
- **Графики и heatmap** — обычный SVG, никакого Cairo.
- **Claude Code лучше всего пишет именно TypeScript/React.** Это не мелочь: львиная
  доля кода в проекте — интерфейс, и качество тут будет заметно выше, чем на PyGObject.
- Бинарь ~10 МБ, память — десятки мегабайт, на твоём ноуте без дискретной GPU это важно.

### 0.2 Где живёт логика

Правило: **всё, что должно быть правильным — в Rust. Всё, что должно быть красивым — в TS.**

```
lokked/
  src/                        # TypeScript + React — только интерфейс
    routes/                   # экраны
    components/               # виджеты
    lib/                      # клиент к Rust-командам, форматирование, хоткеи
    styles/
  src-tauri/
    src/
      core/                   # чистый Rust, БЕЗ tauri:: и sqlx:: — покрыт тестами
        clock.rs              # trait Clock + RealClock + FakeClock
        dayline.rs            # границы учебного дня, разбивка сессий по дням
        timer.rs              # конечный автомат таймера и pomodoro-циклов
        scheduler.rs          # выбор карточек в разных режимах
        stats.rs              # агрегации
        srs.rs                # интервальное повторение (позже)
      db/                     # SQLite: пул, миграции, репозитории
      platform/               # trait PlatformServices + linux.rs / windows.rs / mobile.rs
      commands.rs             # #[tauri::command] — тонкий слой, только вызовы core/db
      lib.rs
    tauri.conf.json
    Cargo.toml
```

`core/` не знает ни про Tauri, ни про базу, ни про UI — это обычная Rust-библиотека,
которую можно тестировать через `cargo test` за миллисекунды. Именно там живут все
места, где приложение может тихо соврать в статистике.

### 0.3 Время: три разные задачи

| Задача | Решение |
|---|---|
| Сколько прошло с начала сессии | **Не** системный монотонный таймер, а разница `now_utc - started_at`, где `started_at` записан один раз при старте |
| Момент времени (история, БД) | UTC, хранить как ISO-8601 текст |
| К какому дню относится | локальная дата + настраиваемая граница дня (`core/dayline.rs`) |

Важное отличие от v1-плана: на мобилке приложение **будет** убито системой или уйдёт
в фон. Поэтому таймер не должен «тикать» — он должен быть **чистой функцией от
`started_at` и списка пауз**. Тогда всё работает одинаково: закрыл крышку ноутбука,
свернул приложение на телефоне, система выгрузила процесс — при возврате время
пересчитывается из timestamp'ов и оказывается верным. Никаких фоновых сервисов
и wake lock'ов не нужно.

Это же снимает главный риск мобильной версии: единственное, что реально требует
фоновой работы — **уведомление о конце помодоро**. Оно решается не фоновым процессом,
а запланированным локальным уведомлением: в момент старта фазы мы знаем, что она
закончится через 25 минут, и сразу планируем уведомление на это время. Если фазу
прервали — отменяем.

UI обновляется через `requestAnimationFrame` (или `setInterval(250)`), но значение
**всегда пересчитывается из timestamp'ов**, никогда не накапливается сложением тиков.

### 0.4 Реалии сборки под каждую платформу

- **Linux** — собирается локально, никаких проблем.
- **Windows** — кросс-компиляция из Linux мучительна. Правильный путь: **GitHub Actions
  с windows-latest раннером**, собирает `.msi`/`.exe` при каждом теге. Бесплатно для
  публичных репозиториев. Настроить на этапе M13, до этого про Windows не думать.
  Требование к системе пользователя: WebView2 (в Windows 11 предустановлен, в Win10 —
  ставится автоматически инсталлятором).
- **Android** — собирается локально на Fedora: Android SDK + NDK + JDK 17 + `cargo tauri android`.
- **iOS** — **требует macOS для сборки и подписи.** Это ограничение Apple, а не Tauri,
  и оно одинаково для любого стека (Flutter, React Native — то же самое). Варианты:
  арендованный mac в облаке (macincloud, MacStadium) или macOS-раннер в GitHub Actions.
  Планировать последним, после того как Android заработает.

### 0.5 Схема БД сразу под синхронизацию

Это самое дорогое, что стоит ретрофитить, и самое дешёвое, что стоит сделать сразу.
Четыре правила, действующие с первой миграции:

1. **Первичные ключи — UUIDv7 (TEXT), а не автоинкремент.** Иначе при слиянии данных
   с телефона и ноутбука ты получишь два разных объекта с `id = 5`.
   UUIDv7 (а не v4) — потому что он сортируется по времени, и индексы не деградируют.
2. **`updated_at TEXT NOT NULL` на каждой таблице.** Без этого нечем разрешать конфликты.
3. **Мягкое удаление: `deleted_at TEXT NULL` вместо `DELETE`.** Иначе удалённая на
   телефоне карточка воскреснет при следующей синхронизации с ноутбука.
   Все запросы — с `WHERE deleted_at IS NULL`.
4. **`sessions` и `reviews` — append-only.** Записи туда только добавляются, никогда
   не редактируются. Такие таблицы синхронизируются тривиально: конфликтов в принципе
   не бывает, слияние — это объединение множеств.

Самой синхронизации в v1 нет. Но когда она понадобится (M15), это будет неделя работы,
а не переписывание всей базы.

## 1. Схема базы данных

SQLite (на всех платформах, включая мобилки). Миграции — нумерованные `.sql` файлы,
версия в `PRAGMA user_version`. Включить `foreign_keys = ON`, `journal_mode = WAL`.

```sql
-- Общие поля во всех таблицах: id TEXT PK (UUIDv7), created_at, updated_at, deleted_at

subjects(
  id TEXT PK, name TEXT NOT NULL, color TEXT, icon TEXT, position INTEGER,
  created_at TEXT, updated_at TEXT, deleted_at TEXT
)

timer_presets(
  id TEXT PK, subject_id TEXT NULL REFERENCES subjects(id),
  name TEXT,
  mode TEXT,                    -- 'countup' | 'countdown' | 'pomodoro'
  work_seconds INTEGER,
  break_seconds INTEGER,
  long_break_seconds INTEGER,
  cycles_before_long INTEGER,
  auto_start_next INTEGER,
  is_default INTEGER,
  created_at TEXT, updated_at TEXT, deleted_at TEXT
)
-- subject_id = NULL → глобальный пресет для всех предметов

sessions(                       -- append-only
  id TEXT PK, subject_id TEXT REFERENCES subjects(id), preset_id TEXT NULL,
  mode TEXT, phase TEXT,        -- 'work' | 'break' | 'long_break'
  started_at TEXT, ended_at TEXT,          -- UTC
  day_key TEXT NOT NULL,                   -- 'YYYY-MM-DD'
  active_seconds INTEGER, paused_seconds INTEGER,
  planned_seconds INTEGER NULL,
  completed INTEGER, interruptions INTEGER DEFAULT 0,
  device_id TEXT,               -- пригодится при синхронизации
  created_at TEXT, updated_at TEXT
)
CREATE INDEX idx_sessions_day ON sessions(day_key);
CREATE INDEX idx_sessions_subject ON sessions(subject_id);

decks(id TEXT PK, subject_id TEXT NULL, name TEXT, description TEXT,
      created_at TEXT, updated_at TEXT, deleted_at TEXT)

cards(
  id TEXT PK, deck_id TEXT REFERENCES decks(id),
  front TEXT NOT NULL,          -- «Теорема Лагранжа о среднем значении»
  back TEXT NOT NULL,           -- формулировка, поддерживает $LaTeX$
  hint TEXT, tags TEXT,
  -- поля SRS, заполняются с M16, до этого NULL
  ease REAL, interval_days REAL, due_at TEXT, reps INTEGER, lapses INTEGER,
  created_at TEXT, updated_at TEXT, deleted_at TEXT
)

reviews(                        -- append-only
  id TEXT PK, card_id TEXT REFERENCES cards(id),
  reviewed_at TEXT, day_key TEXT,
  result TEXT,                  -- 'again' | 'hard' | 'good' | 'easy' (галочка = 'good')
  correct INTEGER,              -- 0/1, производное — для простой статистики
  mode TEXT,                    -- 'classic' | 'blitz' | 'marathon' | 'weak'
  think_ms INTEGER, total_ms INTEGER,
  device_id TEXT, created_at TEXT
)
CREATE INDEX idx_reviews_card ON reviews(card_id);
CREATE INDEX idx_reviews_day ON reviews(day_key);

settings(key TEXT PK, value TEXT, updated_at TEXT)
```

Статистику по карточке («сколько раз всего угадал») **не хранить счётчиком** — считать
запросом по `reviews`. Счётчики рассинхронизируются при любой ошибке или при слиянии
данных с двух устройств, лог событий — нет.

## 2. «Обнуление в 12 ночи» — это фильтр, а не удаление

Ничего не стирается. У каждой сессии и каждого ответа есть `day_key` — локальная дата
с учётом настройки **«начало учебного дня»** (по умолчанию `00:00`, но полезно уметь
поставить `04:00`: если сидишь до трёх ночи, это всё ещё вчерашний день).

Что должно быть реализовано явно:

- Экран «Сегодня» = `WHERE day_key = today()`. И всё.
- Сессия, доживающая до границы, **режется на два сегмента** при записи в БД, чтобы
  дневные суммы были честными. Сам таймер при этом не прерывается.
- UI обновляется на границе: таймер до ближайшей границы (пересчитывать каждый раз,
  не `86400`), плюс принудительный пересчёт при возврате приложения из фона
  (`visibilitychange`) и при пробуждении системы.
- Переход на летнее время не должен ничего ломать. Тесты на дни длиной 23 и 25 часов —
  обязательны.
- Часовой пояс берётся системный; при перелёте `day_key` уже записанных сессий
  не пересчитывается.

## 3. Функциональные требования

### 3.1 Адаптивность — с первого дня

Это ключевое требование, которое делает мобильную версию дешёвой. Каждый экран должен
работать и на 380px, и на 1400px. Практически:

- Верстать **mobile-first**: сначала одна колонка, потом media-запросы расширяют.
- Навигация: на мобилке — нижний таб-бар, на десктопе — боковая панель. Один компонент,
  два состояния.
- Все интерактивные элементы — минимум 44×44px (палец), даже на десктопе это не мешает.
- Никаких hover-only взаимодействий: всё, что доступно по наведению, должно быть
  доступно и по тапу.
- Учитывать safe-area (вырезы и жестовая полоса на телефонах) через `env(safe-area-inset-*)`.
- Проверять каждый экран в DevTools в режиме 390×844 сразу, а не «потом адаптируем».

### 3.2 Главный экран
Список предметов с цветом, названием, временем за сегодня и кнопкой «Старт».
Сверху — суммарное время за день и streak (дней подряд с учёбой ≥10 минут).
Отдельный вход в раздел карточек и в статистику.

### 3.3 Экран таймера
- Крупные цифры, обязательно `font-variant-numeric: tabular-nums` — иначе цифры прыгают.
- Кнопки: пауза/продолжить, «отвлёкся» (+1 к interruptions, таймер не останавливая),
  стоп, переход в чёрный экран.
- Для Pomodoro: круговой SVG-прогресс и подпись «работа 2/4».
- На смене фазы: уведомление + короткий звук.
- Во время фазы `work` — не давать экрану гаснуть (см. 3.8). **Обязательно отпускать**
  на паузе и в перерыве.

### 3.4 Режим «чёрный экран» (zen)
- Фон `#000000`, по центру — время с начала учёбы, ниже мелко и приглушённо название
  предмета. Больше на экране нет ничего.
- На десктопе — реальный fullscreen окна. На мобилке — immersive-режим со скрытыми
  системными панелями.
- Через 5 секунд бездействия курсор прячется, цвет цифр гаснет до `#8a8a8a`
  (не выжигает OLED и меньше отвлекает). Любое движение/тап — возвращает.
- Десктоп: `Esc` — выход, `Space` — пауза, `Q` — завершить. Мобилка: тап по центру —
  пауза, свайп вниз — выход.
- Настройки: «показывать только минуты», размер шрифта.

### 3.5 Карточки: редактор
- Дерево предмет → колода → карточки, поиск по тексту, фильтр по тегам.
- **Массовый импорт текстом** — критично: руками 300 определений никто не введёт.
  Формат (разделители настраиваемые):
  ```
  Теорема Лагранжа
  ---
  Если $f$ непрерывна на $[a,b]$ и дифференцируема на $(a,b)$, то
  $\exists c \in (a,b): f'(c) = \frac{f(b)-f(a)}{b-a}$
  ===
  Следующая карточка
  ---
  ...
  ```
  Предпросмотр перед импортом с числом распознанных карточек. Экспорт в тот же формат.
  Это позволит надиктовывать определения голосом в текстовый файл и заливать пачками.
- **Формулы: KaTeX**, inline `$...$` и блочные `$$...$$`. Работает одинаково на всех
  платформах, рендерится мгновенно.
- Базовый markdown (`**жирный**`, `*курсив*`, списки) — через лёгкий парсер,
  результат обязательно санитизировать перед вставкой.

### 3.6 Карточки: режимы

| Режим | Как работает |
|---|---|
| **Классика** | Показан `front`. Проговариваешь ответ вслух. `Space` / тап — раскрыть `back`. Дальше самооценка: `1` не помню, `2` с трудом, `3` знаю (галочка), `4` легко. Галочка визуально главная. |
| **Блиц** | N секунд на карточку (по умолчанию 20). Убывающее SVG-кольцо, последние 5 секунд красным, не успел → автоматически `again`. Счёт: +10 за верный, множитель за серию (×1.5 с 5 подряд, ×2 с 10), в конце итог и рекорд колоды. |
| **Марафон** | Вся колода без повторов, прогресс-бар, финальный отчёт с ошибками и кнопкой «прогнать ошибки ещё раз». |
| **Только слабые** | 20 карточек с худшей точностью за 30 дней при ≥3 показах. |

Общее: полное управление с клавиатуры на десктопе, свайпы и крупные кнопки на мобилке.
Никакого ввода текста — ты отвечаешь **вслух**, оценка ручная и честная. В этом и смысл:
работает активное припоминание, а не печатание ответа в поле.

### 3.7 Статистика
- **День**: время по предметам (горизонтальные бары), число завершённых помодоро,
  карточки и точность.
- **Неделя / месяц / всё время**: график по дням + heatmap в стиле GitHub (обычный SVG).
- **По карточке**: всего показов, угадано раз, точность %, последние 10 ответов
  цепочкой зелёных/красных точек, среднее время припоминания, текущая серия.
- **Топ проблемных**: 20 карточек с худшей точностью (при ≥3 показах).
- Экспорт в CSV.

### 3.8 Платформенный слой

В `src-tauri/src/platform/` — trait `PlatformServices` и три реализации:

| Возможность | Linux | Windows | Android |
|---|---|---|---|
| Не гасить экран | D-Bus портал Inhibit / `org.freedesktop.ScreenSaver` | `SetThreadExecutionState` | wake lock через плагин |
| Уведомления | `tauri-plugin-notification` | то же | то же + разрешение POST_NOTIFICATIONS |
| Запланированные уведомления | таймер в процессе | то же | планировщик ОС |
| Сон/пробуждение системы | сигнал `PrepareForSleep` от `login1` | `WM_POWERBROADCAST` | не нужен |
| Глобальные хоткеи | GNOME Settings → свои комбинации → CLI (на Wayland иначе никак) | `tauri-plugin-global-shortcut` | не применимо |
| Автозапуск | `.desktop` в autostart | реестр | не применимо |

Код, вызывающий эти функции, работает только через trait. Ни одного `#[cfg(target_os)]`
за пределами `platform/`.

## 4. Подготовка окружения

```bash
# Rust
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

# Node (через nvm или dnf)
sudo dnf install nodejs npm

# Системные зависимости Tauri для Fedora
sudo dnf group install "C Development Tools and Libraries"
sudo dnf install webkit2gtk4.1-devel openssl-devel curl wget file \
                 libappindicator-gtk3-devel librsvg2-devel \
                 gtk3-devel libsoup3-devel

# Tauri CLI
cargo install tauri-cli --version "^2.0"
```

Если при запуске окно окажется чёрным или будет мигать — известная особенность
WebKitGTK на Wayland, лечится переменной `WEBKIT_DISABLE_DMABUF_RENDERER=1`
(на Intel-графике обычно не требуется, но знай про неё).

Android (понадобится на M14, не сейчас): JDK 17, Android Studio с SDK и NDK,
переменные `ANDROID_HOME` / `NDK_HOME`, плюс
`rustup target add aarch64-linux-android armv7-linux-androideabi i686-linux-android x86_64-linux-android`.

## 5. Начальный промпт для Claude Code

Открой Claude Code в пустой папке `~/projects/lokked`, **включи plan mode**
(Shift+Tab дважды) и дай ровно это:

---

> Мы начинаем проект Lokked — кросс-платформенное приложение для учёбы
> (таймеры по предметам + учебные карточки + статистика).
> Целевые платформы по порядку: Linux (Fedora 43, GNOME, Wayland) → Windows → Android → iOS.
> Стек: Tauri 2, Rust в бэкенде, TypeScript + React + Vite во фронтенде, SQLite для данных.
>
> Твоя задача на этот этап — только скелет проекта, без бизнес-логики.
>
> Сделай:
> 1. Инициализируй Tauri 2 проект с шаблоном React + TypeScript + Vite. Название
>    приложения Lokked, identifier `com.lokked.app`.
> 2. Создай структуру каталогов:
>    - `src-tauri/src/core/` — чистая Rust-логика (позже: clock, dayline, timer,
>      scheduler, stats). Пока только `mod.rs` с заглушками модулей.
>    - `src-tauri/src/db/` — работа с SQLite и миграции.
>    - `src-tauri/src/platform/` — trait `PlatformServices` с методами
>      `inhibit_sleep()`, `release_sleep()`, `notify(title, body)` и заглушками

## 6. Содержимое `CLAUDE.md`

```markdown
# Lokked

Кросс-платформенное приложение для учёбы: таймеры по предметам + учебные карточки +
статистика. Платформы по приоритету: Linux (Fedora 43, GNOME, Wayland) → Windows →
Android → iOS.

## Стек
Tauri 2 · Rust (бэкенд) · TypeScript + React + Vite + Tailwind (фронтенд) · SQLite.
Тесты: `cargo test` (Rust), Vitest (фронтенд).

## Команды
- Разработка: `npm run tauri dev`
- Сборка: `npm run tauri build`
- Тесты: `cargo test --manifest-path src-tauri/Cargo.toml` и `npm test`
- Линтеры: `cargo clippy -- -D warnings`, `cargo fmt`, `npm run lint`

## Архитектурные правила (не нарушать)

1. **Разделение слоёв.** В `src-tauri/src/core/` запрещены импорты `tauri::`, `sqlx::`,
   `rusqlite::` и любого ввода-вывода. Это чистая библиотека: вся бизнес-логика
   (таймер, границы дня, выбор карточек, агрегации) живёт там и покрыта тестами.
   `commands.rs` — тонкий слой: распарсил аргументы, вызвал core/db, вернул результат.
   Во фронтенде бизнес-логики нет, только отображение.

2. **Время.** Длительность = `now_utc - started_at` минус паузы, вычисляется как
   чистая функция от timestamp'ов. НИКОГДА не накапливать время сложением тиков —
   приложение будет выгружаться из памяти на мобилке, и накопленное потеряется.
   Все обращения к текущему времени в `core/` идут через trait `Clock`, чтобы тесты
   использовали `FakeClock`. Прямые вызовы `Utc::now()` внутри `core/` запрещены.

3. **Схема БД — сразу под будущую синхронизацию.**
   - Первичные ключи: UUIDv7 в TEXT. Никакого AUTOINCREMENT.
   - На каждой таблице: `created_at`, `updated_at`, `deleted_at`.
   - Удаление только мягкое: `deleted_at = now`, все выборки с `WHERE deleted_at IS NULL`.
   - `sessions` и `reviews` — append-only, записи не редактируются.
   - Схема меняется только новой миграцией в `src-tauri/migrations/`. Существующие
     миграции не редактировать никогда.

4. **Данные дня НЕ удаляются в полночь.** «Сегодня» — это фильтр по `day_key`.

5. **Платформенный код.** Всё, что зависит от ОС, живёт только в
   `src-tauri/src/platform/` за trait `PlatformServices`. `#[cfg(target_os = ...)]`
   за пределами этого каталога запрещён.

6. **Адаптивность.** Каждый экран верстается mobile-first и должен корректно работать
   на ширине 380px и 1400px. Интерактивные элементы минимум 44×44px. Никаких
   взаимодействий, доступных только по hover. Проверять оба размера при каждом
   UI-изменении.

7. **Размер файлов.** Больше 400 строк — разбивать.

## Зависимости
Новые библиотеки не добавлять без явного разрешения. Разрешены: стандартные библиотеки,
Tauri и его официальные плагины, React, Tailwind, KaTeX (формулы), uuid, chrono,
rusqlite/sqlx, serde. Графики рисуем сами обычным SVG — библиотеки для чартов не нужны.

## Стиль работы
- Один этап = одна ветка = один коммит с осмысленным сообщением.
- Для кода в `core/` сначала тесты, потом реализация.
- После изменений всегда прогонять тесты и `cargo clippy -- -D warnings`.
- Если требование неоднозначно — задать вопрос, а не догадываться.
- Не трогать код, не относящийся к текущей задаче.
```

## 7. Этапы

По одному за раз. Перед каждым — plan mode, прочитать план, поправить, разрешить.
После каждого — тесты, проверка руками, коммит, `/clear`.

### M0 — Скелет
Промпт из раздела 5. *Готово, когда* `npm run tauri dev` открывает окно и `ping` отвечает.

### M1 — Часы и учебный день

> Реализуй `core/clock.rs`: trait `Clock` с методом `now_utc() -> DateTime<Utc>`,
> реализации `RealClock` и `FakeClock` (у последней время двигается методами
> `advance(Duration)` и `set(dt)`).
> Реализуй `core/dayline.rs`: `day_key(moment_utc, tz, day_start) -> String` ('YYYY-MM-DD'),
> `next_boundary(moment_utc, tz, day_start) -> DateTime<Utc>`,
> `split_by_day(start, end, tz, day_start) -> Vec<Segment>` — разбивает интервал
> на сегменты по учебным дням.
> Тесты обязаны покрывать: границу дня, смещённую на 04:00; интервал через полночь;
> переход на летнее время (день 23 часа) и обратно (25 часов); интервал длиннее суток.

Это фундамент всей статистики — тесты здесь не формальность.

### M2 — База данных

> Реализуй `src-tauri/src/db/`: подключение к SQLite (WAL, foreign_keys=ON, путь через
> tauri path API), систему миграций на `PRAGMA user_version` с файлами в
> `src-tauri/migrations/`, и миграцию 001 по схеме из PLAN.md раздела 1 —
> с UUIDv7-ключами, полями created_at/updated_at/deleted_at и мягким удалением.
> Репозитории `SubjectRepo`, `PresetRepo`, `SessionRepo` с CRUD.
> Тесты на БД в памяти: применение миграций с нуля, идемпотентность повторного запуска,
> мягкое удаление скрывает записи из выборок, CRUD каждого репозитория.

### M3 — Движок таймера

> Реализуй `core/timer.rs` — конечный автомат сессии.
> Состояния: `Idle`, `Running`, `Paused`, `Finished`. Фазы: `Work`, `Break`, `LongBreak`.
> Режимы: `CountUp`, `CountDown`, `Pomodoro` (work → break, каждые N циклов long_break,
> флаг auto_start_next).
> API: `start`, `pause`, `resume`, `stop`, `skip_phase`, `mark_interruption`,
> `state_at(now) -> TimerState { elapsed, remaining, phase, cycle, finished }`.
> Ключевое требование: `state_at` — чистая функция от `started_at`, списка интервалов
> пауз и текущего времени. Никакого внутреннего счётчика тиков. Состояние должно
> сериализоваться в JSON и восстанавливаться без потери времени — приложение будет
> выгружаться из памяти на мобилке.
> Тесты на FakeClock: полный цикл 25/5 с длинным перерывом после 4-го; пауза и
> возобновление не теряют и не добавляют секунд; сериализация→восстановление→
> `state_at` даёт то же значение; «пропажа» приложения на час корректно учитывается.

### M4 — Дизайн-система и оболочка UI

> Собери каркас интерфейса: адаптивная навигация (нижний таб-бар до 768px,
> боковая панель выше), роутинг между экранами «Учёба», «Карточки», «Статистика»,
> «Настройки». Тёмная тема как основная, светлая — опцией.
> Определи в Tailwind набор токенов: цвета, радиусы, типографику, и компоненты
> Button, Card, Dialog, Input, Select, EmptyState — их дальше переиспользуют все экраны.
> Проверь верстку на 390×844 и 1440×900.

### M5 — Предметы и пресеты

> Экран «Учёба»: список предметов с цветом, названием, временем за сегодня и кнопкой
> «Старт». Диалоги создания/редактирования предмета (название, цвет из палитры, иконка)
> и пресетов таймера (режим, длительности, число циклов, auto_start_next, «по умолчанию»).
> Пустое состояние с призывом добавить первый предмет.
> Всё через tauri-команды и репозитории из M2.

### M6 — Экран таймера

> Экран активной сессии: крупные цифры с tabular-nums, предмет и фаза, кнопки
> пауза/продолжить, «отвлёкся», стоп, переход в чёрный экран.
> Для pomodoro — круговой SVG-прогресс и подпись «работа 2/4».
> Обновление раз в 250 мс, значение всегда из `state_at(now)`.
> На смене фазы — уведомление через tauri-plugin-notification и короткий звук.
> Во время фазы work запрашивать у `PlatformServices` запрет засыпания экрана,
> отпускать на паузе, в перерыве и при завершении.
> По завершении писать сессию в БД, разбивая по дням через `core::dayline::split_by_day`.
> Обработать возврат приложения из фона (`visibilitychange`): пересчитать состояние
> и, если прошло больше 10 минут, показать диалог «Тебя не было N минут — засчитать
> это время или отбросить?».

### M7 — Чёрный экран

> Полноэкранный режим: фон #000, по центру время с начала сессии, ниже мелко
> и приглушённо название предмета. Больше ничего.
> На десктопе — реальный fullscreen окна через tauri API. На мобилке — immersive-режим
> со скрытыми системными панелями.
> Через 5 секунд бездействия прятать курсор и гасить цвет цифр до #8a8a8a;
> любое движение или тап возвращает.
> Десктоп: Esc — выход, Space — пауза, Q — завершить. Мобилка: тап — пауза,
> свайп вниз — выход.
> Настройки: «показывать только минуты», размер шрифта.

### M8 — «Сегодня» и граница дня

> Сводка за сегодня на главном экране: суммарное время, разбивка по предметам,
> число завершённых помодоро, streak (дней подряд с ≥10 минутами).
> Всё запросами по `day_key`, ничего не удаляется.
> Автообновление на границе дня: таймер до ближайшей границы через
> `core::dayline::next_boundary` (пересчитывать каждый раз), плюс принудительный
> пересчёт при возврате из фона.
> Активная сессия через границу не прерывается, но время корректно делится между днями.
> В настройки — «Начало учебного дня» (по умолчанию 00:00).

### M9 — Карточки: модель, редактор, импорт

> Управление колодами и карточками: дерево предмет → колода → карточки, таблица
> с поиском и фильтром по тегам, диалог создания/редактирования (front, back, hint, теги).
> Импорт из текста: карточки разделены `===`, стороны — `---`, разделители настраиваемые,
> предпросмотр с числом распознанных карточек. Экспорт в тот же формат.
> Формулы через KaTeX: inline `$...$` и блочные `$$...$$`, с fallback на исходный текст
> при ошибке парсинга. Базовый markdown (жирный, курсив, списки) с обязательной
> санитизацией HTML перед вставкой.
> Парсер импорта реализуй в `core/` на Rust и покрой тестами: пустые карточки,
> лишние разделители, разделитель внутри текста, CRLF, невалидный LaTeX.

### M10 — Карточки: классика

> Экран прохождения: показан front, подсказка «проговори ответ вслух, затем Space».
> По Space/тапу раскрывается back. Затем четыре оценки: 1 не помню, 2 с трудом,
> 3 знаю, 4 легко; галочка (3) визуально главная. Управление с клавиатуры и тапом.
> Каждый ответ пишется в `reviews` с think_ms (до раскрытия) и total_ms.
> Перемешивание — в `core/scheduler.rs`, с сидируемым генератором для тестируемости.
> Финальный экран: сколько карточек, точность, время, список ошибок, «повторить ошибки».

### M11 — Карточки: блиц, марафон, слабые

> Поверх M10:
> — Блиц: N секунд на карточку (по умолчанию 20), убывающее SVG-кольцо, последние
>   5 секунд красным, истекло → `again`. Счёт: +10 за верный, ×1.5 с 5 подряд,
>   ×2 с 10; в конце итог и рекорд колоды в `settings`.
> — Марафон: вся колода без повторов, прогресс-бар, финальный отчёт.
> — Только слабые: 20 карточек с худшей точностью за 30 дней при ≥3 показах.
> Выбор карточек и подсчёт очков — в `core/scheduler.rs` и `core/stats.rs` с тестами.
> Граничные случаи: пустая колода, одна карточка, все карточки новые.

### M12 — Статистика

> Три вкладки:
> 1. Время: бары по предметам за день/неделю/месяц/всё, heatmap по дням в стиле GitHub
>    (обычный SVG, без библиотек), streak.
> 2. Карточки: точность по дням, число ответов, топ-20 проблемных.
> 3. По карточке: всего показов, угадано раз, точность %, последние 10 ответов
>    цепочкой зелёных/красных точек, среднее время припоминания, текущая серия.
> Агрегации — чистые функции в `core/stats.rs` плюс SQL в `db/`, с тестами на
> граничные случаи: ноль ответов, один ответ, все неправильные.
> Кнопка «Экспорт в CSV».

### M13 — Платформенный слой для Linux и сборка

> Реализуй `platform/linux.rs`: запрет засыпания экрана через D-Bus портал Inhibit
> (с fallback на `org.freedesktop.ScreenSaver`), подписка на сигнал `PrepareForSleep`
> от `org.freedesktop.login1` с постановкой сессии на паузу и диалогом после пробуждения.
> Добавь CLI-аргументы `--toggle`, `--zen`, `--stop`, передаваемые в уже запущенный
> экземпляр (single instance plugin), и опиши в README, как повесить их на глобальную
> горячую клавишу через GNOME Settings → Клавиатура → Свои комбинации: на Wayland
> приложение не может перехватывать клавиши самостоятельно.
> Автобэкап БД при старте: копия в `backups/`, хранить последние 7.
> Настрой сборку `.rpm` и AppImage.

### M14 — Windows

> Реализуй `platform/windows.rs`: запрет засыпания через `SetThreadExecutionState`,

> Проверь, что пути к БД и конфигу корректны на Windows (AppData), что разделители

*Проверять придётся на реальной Windows или в виртуалке — тут без вариантов.*

### M15 — Android

> Инициализируй Android-таргет (`cargo tauri android init`).
> Реализуй `platform/mobile.rs`: wake lock на время фазы work, запрос разрешения

> (с отменой при прерывании) — фоновый сервис не использовать, состояние таймера
> восстанавливается из timestamp'ов.
> Immersive-режим для чёрного экрана. Обработка кнопки «назад».
> Проверь, что все экраны корректны на 360×640 и с вырезом, что safe-area учтена,
> и что БД создаётся в правильном каталоге приложения.
> Иконки и splash-screen для всех плотностей.

### M16 — Синхронизация (когда появятся два устройства)

> Реализуй синхронизацию между устройствами. Схема к ней уже готова: UUIDv7-ключи,

### M17 — Интервальное повторение (опционально)

## 8. Как вести работу с Claude Code

- **Plan mode перед каждым этапом.** Shift+Tab дважды → промпт → прочитать план →
  поправить, если он тащит лишние зависимости или лезет в чужие файлы → разрешить.
- **Один этап — одна ветка, один коммит.** Откатывать дёшево.
- **`/clear` между этапами.** Контекст от M5 при работе над M11 только мешает.
- **UI Claude Code не видит.** На UI-этапах проверяешь руками и возвращаешься
  с конкретикой: «кнопка Стоп не сохраняет сессию», а не «выглядит криво».
- **Тесты в `core/` — не формальность.** Именно там приложение может тихо соврать
  в статистике. Требуй тесты до реализации.
- **Новые зависимости — почти всегда нет.** SVG рисует графики, стандартная библиотека
  парсит текст, SQLite считает агрегации.
- **Обновляй `CLAUDE.md`** после каждого этапа, если появились новые команды или правила.

## 9. Что сознательно не входит в v1

Аудио и картинки в карточках, шеринг колод, импорт из Anki, распознавание речи для
автопроверки ответов, ачивки сверх блица, виджеты, статистика с ИИ-анализом.
Каждый пункт легко съедает месяц до того, как ты хоть раз воспользуешься таймером.

Порядок такой: рабочий Linux-v1 → пользуешься им неделю → Windows → Android →
и только потом решаешь, чего реально не хватает.
